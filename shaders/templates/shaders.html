Les shaders, partout ✨

C’est quoi un shader ?

  • Petit programme exécuté sur le GPU
    (massivement parallèle)
  • ⚖️ CPU vs GPU :
    CPU → quelques cœurs polyvalents, rapides mais peu nombreux
    GPU → centaines/milliers de cœurs spécialisés, parfaits pour traiter en parallèle pixels, vertices, etc.
  • Exemple concret :
    Full HD @60 fps = ~2 Mpx × 60 ≈ 124 millions de pixels/seconde
  • Compilé à l’exécution par le driver GPU
  • Mise en cache possible
    (évite de recompiler à chaque lancement)
➡️ Insister sur le parallélisme : un fragment shader s’exécute pour des milliers/millions de pixels en même temps. ➡️ Comparaison d’architecture : CPU = ~8–32 cœurs, polyvalents. GPU = centaines/milliers de cœurs, spécialisés pour exécuter la même opération en masse. ➡️ Exemple qui frappe : en Full HD à 60 fps, le GPU doit colorer environ 124 millions de pixels chaque seconde. ➡️ Souligner que c’est impensable pour un CPU seul, mais parfait pour l’architecture GPU.

Les 3 types principaux

  • Vertex ➡️ déforme ou place les sommets (vertices) (ex : onduler un plan)
  • Fragment/Pixel ➡️ calcule la couleur par pixel (éclairage, post-FX)
  • Compute ➡️ calcul général (blur, physique, IA, génération procédurale)

    • Pipeline graphique:

👉 Pour la suite, on va se focaliser sur le Fragment shader.

➡️ Bien insister : Vertex shader → Rasterization → Fragment shader. ➡️ La rasterization transforme la géométrie (triangles) en fragments (pixels potentiels). ➡️ Le Compute shader est hors de ce pipeline, utilisé pour des calculs génériques. ➡️ Une image du pipeline graphique peut renforcer l’explication (Input Assembly → Vertex → Rasterizer → Fragment → Output).

Formats & petite histoire

Hier

  • 🎮 Années 90 : pipeline fixe (aucun shader)
  • 🔧 Début 2000 : assembleur GPU (ARB/NV)
  • 💡 Milieu 2000 : premiers langages haut-niveau → GLSL (OpenGL), HLSL (DirectX)

Aujourd’hui

  • GLSL (OpenGL/ES) • HLSL (DirectX)
  • MSL (Apple/Metal) • WGSL (WebGPU / wgpu / Bevy)
  • Shaders partout : jeux, rendu 3D, compute, web

Intermédiaires & toolchains

  • SPIR-V (Vulkan, WebGPU) • DXIL (DirectX)
  • 🌉 Conversion/transpilation fréquente entre formats
  • Idée clé : concepts communs, mais APIs/langages varient selon la plateforme
  • Exemple : écrire en HLSL → compiler vers SPIR-V → exécuter sur Vulkan
➡️ Expliquer l’évolution : pipeline fixe → assembleur GPU → langages haut-niveau → formats portables. ➡️ Souligner que les langages divergent (GLSL/HLSL/MSL/WGSL) mais les concepts de shaders restent les mêmes. ➡️ SPIR-V et DXIL jouent le rôle d’IR (Intermediate Representation), comme LLVM en compilation CPU. ➡️ Ne pas rentrer dans les détails des toolchains, juste donner la big picture.

Hello World (ShaderToy)

void mainImage(out vec4 c, in vec2 p){
  vec2 uv = p / iResolution.xy;                 // <-- UV (0..1)
  c = vec4(uv, 0.5 + 0.5*sin(iTime), 1.0);      // <-- uniforms (temps, résolution)
}
UV : coordonnées normalisées de texture ∈ [0,1]². Servent à échantillonner des images, ou à se repérer sur l’écran.
Uniformes : valeurs globales, lecture seule, identiques pour tous les pixels durant un draw (ex : iTime, iResolution, textures, matrices…).
Dire que ShaderToy passe gl_FragCoord via p, mais expose directement iTime/iResolution.

Décorticage express : Wave (image dans iChannel0) 

void mainImage(out vec4 c, in vec2 p){
  vec2 uv = p / iResolution.xy;
  float w = sin(uv.y*10.0 + iTime*2.0)*0.02; // période + vitesse + amplitude
  vec3 col = texture(iChannel0, uv + vec2(w,0)).rgb; // déformation horizontale
  c = vec4(col,1.0);
}

Variante « wow » : tunnel en 10 lignes (sin/cos + polar coords).

Montrer comment toucher une seule ligne (uv.y) rend l’effet lisible et pédagogique.

Raymarching : 3D sans maillage

  • Pour chaque pixel : lancer un rayon, avancer par pas jusqu’à toucher la scène
  • SDF : fonction distance → pas sûr (sphere tracing)
  • Heightfield : carte de hauteur H(x,z) → pas adaptatif sur pos.y − H
  • Arrêt : distance < ε (hit) · trop loin (miss) · max steps 
float sdSphere(vec3 p,float r){return length(p)-r;}
float march(vec3 ro, vec3 rd){
  float t=0.0; for(int i=0;i<96;i++){
    float d=sdSphere(ro+rd*t,1.0); if(d<0.001) return t; t+=d; if(t>20.0)break;}
  return -1.0;
}
Résumer : SDF = rapide/stable ; heightfield = terrain. Parler de normales via différences finies, shadows/AO.

Intégrer dans Bevy (WGSL)

@group(1) @binding(0) var tex: texture_2d<f32>;
@group(1) @binding(1) var smp: sampler;
struct U { time: f32, res: vec2<f32>; };
@group(1) @binding(2) var<uniform> u: U;
@fragment fn fs(@builtin(position) pos: vec4<f32>)->@location(0) vec4<f32>{
  let uv = pos.xy / u.res; let w = sin(uv.y*10.0 + u.time*2.0)*0.02;
  let col = textureSample(tex, smp, uv + vec2(w,0.0)); return vec4(col,1.0);
}
  • Ajouter Material2d custom avec texture + uniformes (temps, résolution…)
  • Concepts identiques à ShaderToy → portables vers Unity/Unreal/Three.js
Invoquer l’analogie ShaderToy↔WGSL : mêmes briques, seuls les bindings changent.

Démo Web (Three.js)

const mat=new THREE.ShaderMaterial({
  uniforms:{ iTime:{value:0}, iResolution:{value:new THREE.Vector3(w,h,1)},
    iChannel0:{value:new THREE.TextureLoader().load('img.jpg')} },
  fragmentShader:`
    uniform float iTime; uniform vec3 iResolution; uniform sampler2D iChannel0;
    void main(){ vec2 uv=gl_FragCoord.xy/iResolution.xy;
      float w=sin(uv.y*10.0+iTime*2.0)*0.02;
      vec3 col=texture2D(iChannel0, uv+vec2(w,0.)).rgb; gl_FragColor=vec4(col,1.0); }`
});

Même logique : uniforms + UV + échantillonnage → effet identique.
